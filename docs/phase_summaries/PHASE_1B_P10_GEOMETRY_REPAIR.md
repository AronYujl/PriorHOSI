## 科学载荷：交互项

**交互 `(A11−A01)−(A10−A00)` 在每一个物体/运动指标上显著且很大，在每一个接触与穿透指标上完全缺席。**

|---|---:|---|
| `end_obj_trans_err` | −3.59914 | [−3.98861, −3.21700] |
| `obj_trans_dist` | −2.99965 | [−3.71084, −2.30046] |
| `trans_dist` | −0.53884 | [−0.83383, −0.24125] |
| `mpjpe` | −0.52311 | [−0.83751, −0.20904] |
| `pelvis_goal_error_cm` | −0.46656 | [−0.74537, −0.17982] |
| `obj_rot_dist` | −0.05831 | [−0.09722, −0.01959] |

跨零（接触 + 穿透 + 足部，共 8 项）：`hand_pen` −0.02009、`human_pen` −0.28942、`hand_pen_ratio`
−0.01600、`human_pen_ratio` −0.01377、`contact_f1` +0.01249、`contact_precision` +0.01044、
`contact_recall` +0.00550、`foot_sliding` +0.02299。

**这个 6/6 对 8/8 的干净劈分本身就是机制证据：两个因子作用在不同的通路上。** 铰链改变的是该项**自身的值**
（把 2 cm 以内的惩罚从可达最小值里拿掉），detach 改变的是**该项梯度落在谁身上**（物体还是手）。
所以它们只在物体/运动指标上相互纠缠，在接触/穿透指标上互不干涉。这比"修复失败了"信息量大得多，
而且**只有把 2×2 跑完才拿得到**——若按原计划两波、并在两个主效应格之后截断，得到的会是两个无法解释的
主效应和零个交互项。

**因此两个主效应单独都不可解读。** detach 的主效应看起来是纯灾难（`end_obj` +1.42835、
`trans_dist` +3.05755），铰链的主效应看起来是全面修复（`end_obj` −1.67421、`obj_trans_dist` −1.76317）；
两者都只是交互项在两个水平上的平均投影。

### 机制读法（作为解释提出，不作为已确立事实）

在**零距离目标**下，模型有两条路满足该项：把手移到物体表面上，或者把**物体**挪一部分到手上。
detach 掐断了物体那条路却没有降低要求，于是模型只能用极端的手部运动去够——全局运动被扭曲
（`trans_dist` +3.33、`pelvis_goal_error_cm` +3.35），物体落点被毁（`end_obj` +3.23）。
铰链把要求放松了 2 cm，detach 才变得可以承受：A11 的 `end_obj` 回到 **4.451**，相对 W3 是
−0.24586（跨零，即"略好但不显著"）。

**所以物体梯度是承重的，但它承重的原因是目标为零距离，而不是它自身携带独立监督。**
预注册当时的判断（该梯度是干扰，物体已由 `object_translation`/`object_rotation`/`object_surface`/
`object_goal` 四个 GT 重建项充分监督）在这个意义上不成立。

## Provenance 隐患（必须记录，以免后来的读者被误导）

A10/A01 **在 `91232ad` 启动**，但它们的 `metrics.json` 记录的 `git_commit` 是 **`5d39ac3`**。
机制已定位：`_git_commit()` 在**写指标时**才实时解析（`code/train_hoi_prior.py:6251`，位于最终指标
组装内），而 `metrics.json` 只在运行结束时写一次。运行期间落地的提交，会**追溯性地**变成该运行被记录的
provenance。A10/A01 运行期间共落地三个提交：`981b9b0`（A11 配置，08-09 18:56）、`b51c3b3`（registry 修复）、
`5d39ac3`（bootstrap 工具）；被记录的只是最后一个。

**这是多 session 并行安排的系统性隐患，不是某一个 session 的失误。** A11 之所以幸免（记录 `981b9b0`，
即其真实启动提交），是因为 AGENTS.md 禁止在可上报运行期间改动 worker 源码，worker 因此被钉住
——**是规则带来的隔离，不是预见**。

**执行的代码可证为 `91232ad` 的**（两个 session 独立复核）：`git diff 91232ad..5d39ac3 -- code/` 只触及
一个文件 `code/config/config_train_hoi_prior_p10_both.yaml`（A11 的配置，A10/A01 从不加载）；
`code/train_hoi_prior.py`、`code/priors/losses.py` 及 A10/A01 各自的配置在该区间内**逐字节相同**。
所以执行的目标函数、数据与训练代码确为 `91232ad`，**2×2 的内部效度完好**；但记录断言了一个运行启动时
尚不存在的提交，且那棵树里含有事后才写的 bootstrap 工具。

**修复属于后续改动，不属于这个已关闭的子阶段**：应在**运行开始时**解析提交并写入 manifest，
而不是在写指标时调用 `git rev-parse HEAD`。

## 下一入口

**P10 排除的：把吸引项的目标重新整形，不是穿透的解法。** 零距离 → 2 cm 铰链没有把穿透显著压下去；
把物体从该项的梯度里摘掉，在零距离目标下是灾难性的，且加上铰链之后也只是回到 W3 附近，
换不来任何穿透收益。剂量（P8-P9c 的八点扫描）与公式（本轮）两条路现在都走完了。

**证据现在指向的两处（陈述为指向，不作为推荐）：**

1. **目标函数里只有吸引子，没有排斥子。** `masked_hand_object_distance_loss` 是把手拉向表面的项；
   整个训练目标中**不存在任何直接惩罚手部顶点进入物体内部的项**。铰链只是让吸引在 2 cm 处停手，
   它不会把已经穿进去的顶点推出来。W3 相对 H0 的穿透 +57% 与本轮的全部结果都与"缺一个排斥项"相容。
2. **穿透可能由手的姿态/朝向驱动，而不是掌关节到表面的距离。** 本轮把该距离的目标从 0 抬到 2 cm、
   甚至把训练侧几何项压到 0.00397，评测侧穿透纹丝不动——这正是"被优化的量与被度量的量不是同一件事"
   的形状。掌关节位置对了而手掌朝向错了，顶点照样进得去。
